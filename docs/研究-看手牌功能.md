# 看手牌功能：图片、HUD 与 HTTP 接入研究

本轮仅研究本地源码与现有文档，未实现 MOD、未部署服务、未运行游戏验证新调用。目标服务为 https://astralpartycards.hiynet.com/ ，服务源码为工作区 AstralPartySpectator。

## 结论

建议新增独立 HandViewerMod：在每个 HUD 玩家条目的头像右侧添加 FairyGUI 按钮，打开只读手牌窗口；通过 UnityWebRequest 请求 Spectator 的 /query，复用一次请求返回的全房间数据；图片优先使用游戏本地 Addressables 资源。

## 服务接口与数据

- `GET /query?id=<URL 编码后的观战码>`，或 `POST /query`，JSON 为 `{ "watchCode": "..." }`。
- `id` 是观战码，不是玩家 ID。客户端现有来源：`GameLogic.RoomInfo.watchCode => info?.WatchCode`。
- QueryController.cs:13–44 定义接口、入参校验、429/503 与 Retry-After。
- SpectatorState.cs:27–36 返回 roomId、sampledUtc、players[]；每位玩家含 playerId（字符串）、slot、handKnown、handCount、handReason、cards[]。
- cards[] 含 cardUid、cardId、purifyNum、isTemp、battleCost。SpectatorCatalog.cs:32–48 在配置可用时补 name、description、baseCost。
- 服务响应目前不提供图片 URL。MOD 可按 cardId 查询本地配置并加载原卡面。
- QueryService.cs:26–53 全局每秒接纳一次，仅一个观战会话执行，另有两个有界等待席位；每次查询会重新登录、观战、读取快照并离开（SpectatorClient.cs:53–68）。
- 现有实现支持国服多人 PVE（MapType 4/12），其他模式被拒绝（SpectatorClient.cs:110–112）。这是当前服务的实现边界。
- 在线 /health 请求被 web_fetch 因域名解析为非公网 IP 拦截，因此本轮未验证线上部署版本与可用性。

## 游戏里怎样显示图片

推荐直接复用游戏资源加载体系：

`cardId → 游戏卡牌配置/卡面 key → TextureLoader → TextureManager → AddressableHelper.LoadAssetAsync<Texture> → NTexture → FairyGUI`

关键源码位于工作区 `decomp_full/`：

- UI/UIManager.cs:390 注册 TextureLoader 为 FairyGUI GLoader 扩展。
- UI/TextureLoader.cs:7–29 调 TextureManager.AsyncLoad(url)，加载成功 AddRef，释放时 ReleaseRef。
- UI/TextureManager.cs:28–78 按 key 缓存 NTexture，Addressables 加载 Texture，最终释放引用与 Addressables handle。
- UI/UICom_Card.cs:76–79 提供 `CreateInstance()`，创建 Common/Com_Card，已有名称、描述、费用、卡面等子控件。
- UI/CommonUIManager.cs:209–239 渲染卡面与描述；:271–290 提供局内 RendererCardInRoom。实现时需要正确解析 CardView/配置，不能仅按文件名猜 key。
- UI/UICom_PlayerInfo.cs:157 的头像也是 `loader_Icon.url = ...ProfilePhoto`。

注意：游戏 GLoader 的 url 在此扩展中是 Addressables key，不能直接填任意 HTTPS 图片地址并假设它会下载。

如确实需要外部图片，可先通过 UnityWebRequestTexture 获取 Texture，再包为 NTexture 并赋给 GLoader.texture。FairyGUI/GLoader.cs:295–315 支持 texture setter；FairyGUI/UIPackage.cs:266–279 已有 UnityWebRequestTexture 加载本地 PNG 的源码先例。新 MOD 的远程图片链仍须真机验证，并明确纹理所有权；不要自行 Dispose 游戏 TextureManager 共享的纹理。

## HUD 按钮挂在哪里

现有结构：

`BattleInfoPanel.ui.com_BattlePlayer.com_Container.com_Player_1..4`

- UI/UIBattleInfo_Com_Player.cs:32–37 按 slot 0..3 绑定 PlayerData。
- UI/UIBattleInfo_Button_PlayerInfo.cs 的 btn_Head / btn_Label 已有头像和详情交互。
- 新按钮建议挂到玩家条目下，与现有点击区域同级，以头像边界为定位锚，读取当前条目的 PlayerData.player.Id。
- 点击时 StopPropagation，避免触发条目父级的选目标/观战动作。EventContext.cs:29–32 和 EventDispatcher.cs:237/250 支持该行为。
- 不覆盖 btn_Label 原监听；跟随玩家条目的显隐与输入门控。UIBattleInfo_Com_Player.cs:116–119 /129–135 有 action mask 与战斗隐藏控制。
- HUD 重建时重新绑定，避免重复按钮；卸载时移除监听和控件。精确坐标、缩放、点击区域尚未真机确认。
- 当前 CombatOddsMod 已使用 RuntimeAssemblyService 反射创建 FairyGUI 控件，可沿用该模式；SDK UiService 的窗口/叠加层登记本身不保证实际渲染。

## 怎么进行网络连接

优先 UnityWebRequest 异步 HTTP，避免阻塞游戏主线程：

1. 在主线程创建 GET 请求、设置合理超时并 SendWebRequest。
2. 通过 MOD Update 检查完成状态，或使用现有 UniTask/协程体系。
3. 读取 result、responseCode、downloadHandler.text，使用游戏现有 SimpleJSON 解析。
4. 校验 roomId 与当前房间一致，以 playerId 查找玩家；请求完成后在主线程更新 UI。
5. 结束、取消、换房与卸载时释放请求，并用房间 generation 丢弃旧响应。

源码先例：Tools/RunTimeRemoteConfigHandler.cs:88–117 使用 Get、timeout、异步 SendWebRequest、SimpleJSON.JSON.Parse 与 finally Dispose；Core/WebServerManager.cs:128–149 使用 JSON POST、UploadHandlerRaw、DownloadHandlerBuffer。

当前 extracted_dlls 只有部分 Unity 模块，未发现 UnityEngine.UnityWebRequestModule / UnityWebRequestTextureModule 的编译引用 DLL。可研究 RuntimeAssemblyService 运行时反射，避免分发多余程序集；反射访问新 API 也必须真机验证。不要因为 netstandard 编译成功就判定 HybridCLR 可执行。新 MOD 应声明 ReadGameState、UI、Network 权限。

## 手牌变动监听与请求合并

- SDK GameEvents.HandChanged 在 GameEvents.cs:89 已提供，但 :451–454 会忽略空 Cards；需要补上变成 0 张的通知。
- HookCardChange :265–278 先发事件再调用游戏 original，因此回调里立即读游戏容器可能得到旧值。回调只标记脏状态，在主线程后续处理。
- 补订阅 HeroAttrUpdated（1040），检查 EffectDatas 的 Card / ConvertCard。单靠 HandChanged 不能覆盖转换与属性同步中的手牌变化。
- 入局初始化请求一次；手牌事件标脏、短暂合并后请求一次全房间；请求期间继续发生变化则标记需再查，完成后再次查询。
- 一个 MOD 只维持一个在途请求。四个按钮共用快照，不能为每人分别发四次请求。
- 429/503 按 Retry-After 退避并保留脏标记。服务限制是全局的，不能仅靠客户端每秒一次保证成功。
- 相同手牌数量也可能发生替换/净化/转换，不能只比较数量。
- handKnown=false 表示数据不可用；与 handKnown=true 且 cards=[] 的真实空手牌必须分别显示。
